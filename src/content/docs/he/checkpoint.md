# Check Point

Check Point הוא סיפור של שרת ניהול: ה־SmartCenter (או דומיין MDS) מחזיק את
מסד האובייקטים — gateways, רשתות, אובייקטי host — בעוד שכל gateway מחזיק
את ה־*runtime* (טבלת ARP, החכרות DHCP). ה־connector קורא את שני הצדדים:
מלאי צד הניהול (מכשירי gateway, אובייקטי רשת כ־subnets, אובייקטי host
ככתובות) **וגם** טבלאות ה־runtime של כל gateway — ראו *טבלאות runtime*
להלן.

ה־Web API של Check Point הוא **RPC מעל POST** — גם קריאות הן POSTs אל
`/web_api/<command>`. ה־connector נשאר לקריאה בלבד *מבנית*: הפקודות
היחידות שהוא יכול להוציא הן `login`, `logout`, חמש קריאות `show-*`
וצמד ה־`run-script`/`show-task` שמשרת את דילוג ה־runtime.
הרשימה נאכפת בקוד — אין בו `set-`, `add-`, `delete-`, `publish` או
`install-policy` להפעיל.

## תפקיד לקריאה בלבד

*נבדק מול ⁦Check Point R82⁩ ו־⁦R81.20⁩ (הסימולטור של המעבדה; ⁦R82.10⁩ כש־⁦Check Point⁩ תכריז עליו כגרסה מומלצת).*

1. ⁦SmartConsole⁩ ← *⁦Manage & Settings⁩* ← *⁦Permissions & Administrators⁩* ← *⁦Permission Profiles⁩* ← *⁦New⁩* ← *⁦Customized⁩*.
2. גישה לאובייקטים: *⁦Read⁩* בכל הקטגוריות, בלי *⁦Write⁩*; תחת *⁦Management⁩* הפעילו **⁦Management API Login⁩**.
3. רק אם רוצים את טבלאות זמן הריצה של השערים (⁦ARP⁩, ⁦DHCP⁩, מנהרות ⁦VPN⁩, רשומת ה־⁦ICA⁩): *⁦Others⁩* ← **⁦Run One Time Script⁩**. דעו מה זה אומר: ההרשאה מריצה סקריפטים ברמת ⁦expert⁩ על כל שער — ⁦LanCompass⁩ שולחת חמש פקודות קריאה קבועות, אבל פרטי התחברות שדלפו עם ההרשאה הזו הם מעטפת ⁦root⁩. מקורות חדשים משאירים את טבלאות זמן הריצה כבויות.
4. *⁦Administrators⁩* ← *⁦New⁩* ← `lancompass-reader`, אימות *⁦Check Point Password⁩* (או מפתח ⁦API⁩), שייכו את הפרופיל, ואז *⁦Publish⁩*.
5. בשרת ⁦Multi-Domain⁩ הגדירו את התחום של המקור.

**מה ⁦LanCompass⁩ קוראת:** פקודות `show-*` של ה־⁦Management API⁩ (מארחים, רשתות, שערים, קהילות ⁦VPN⁩, ופעם ביום, אם סומן, בסיסי הכללים של הגישה ושל ה־⁦NAT⁩), בהפעלה שנפתחת `read-only`; עם טבלאות זמן הריצה — חמש קריאות `run-script` קבועות.

## לפני שמתחילים

- **שרת ניהול** — SmartCenter (דומיין יחיד) או דומיין MDS. ה־Web API רץ על
  הניהול, לא על ה־gateways. גרסה R80.10 ומעלה; R81.x מומלץ.
- **זמינות רשת** — מכונת ה־⁦LanCompass⁩ חייבת להגיע לשרת הניהול ב־TCP/443 (או
  בפורט ה־web api שהוגדר).
- **TLS** — Gaia מגיע עם תעודה self-signed. יש לתכנן לכבות את *verify TLS*
  במקור, או להתקין תעודה חתומה-CA בפורטל הניהול.
- **כ־15 דקות** ב־SmartConsole + Gaia.

## שלב 1 — הפעלת ה־Management API

ה־Web API כבוי עד שמדליקים אותו ומגדירים מי רשאי לקרוא לו.

**דרך פורטל Gaia** (הדרך הקלה):

1. גלשו ל־`https://<mgmt>` → התחברו → **Manage & Settings → Blades →
   Management API** (בחלק מהגרסאות: **Network Management → Management
   API**).
2. סמנו **Enable web API**.
3. הגדירו **Access permissions**: עדיף **"Only the following IP
   addresses"** עם כתובת ה־⁦LanCompass⁩. `All IP addresses` יעבוד אבל מרחיב את
   שטח התקיפה — ההרשאה הנכונה היא ACL כאן *וגם* משתמש לקריאה בלבד בשלב 2.
4. שמרו.

**דרך ה־CLI** (expert mode בשרת הניהול):

```bash
api status                 # האם רץ? איזה פורט?
mgmt_cli set web-api-config enable true   # או דרך clish: set web api enabled true
```

בדקו את הפורט: `api status` מדפיס אותו (ברירת מחדל **443**). ב־MDS מריצים
את זה לכל דומיין (`mdsenv <domain>`) — ה־API הוא per-domain.

מוודאים שהוא עונה:

```bash
curl -sk https://<mgmt>/web_api/login -H 'Content-Type: application/json' -d '{}'
# → {"message":"Missing header: [X-chkp-sid] or authentication"...} — ה-API
# חי; ההזדהות נבדקת בשלב 3.
```

## שלב 2 — יצירת administrator לקריאה בלבד

אף פעם לא נותנים לאינטגרציה את ה־admin שלכם. בונים משתמש ייעודי עם
פרופיל מותאם שקורא אובייקטים ומתחבר ל־⁦API⁩ — ומריץ סקריפטים רק אם רוצים
את טבלאות זמן הריצה:

1. ⁦SmartConsole⁩ ← **⁦Manage & Settings⁩ ← ⁦Permissions & Administrators⁩ ←
   ⁦Permission Profiles⁩ ← ⁦New⁩ ← ⁦Customized⁩**.
2. גישה לאובייקטים: **⁦Read⁩** בכל הקטגוריות, **⁦Write⁩** באף אחת. תחת
   *⁦Management⁩* הפעילו **⁦Management API Login⁩**. הפרופיל לא יכלול הרשאות
   כתיבה של ⁦Manage Sessions⁩ או התקנת מדיניות.
3. **רק לטבלאות זמן ריצה:** תחת *⁦Others⁩* סמנו **⁦Run One Time Script⁩**.
   דעו מה המשמעות: `run-script` רץ ברמת ⁦expert⁩ על כל שער. ⁦LanCompass⁩
   שולחת רק את פקודות הקריאה הקבועות שלה, אבל פרטי גישה שדלפו עם ההרשאה
   הזו הם מעטפת ⁦root⁩ על השערים — השאירו אותה בחוץ אלא אם מפעילים את
   טבלאות זמן הריצה (הן כבויות במקור חדש).
4. **⁦Administrators⁩ ← ⁦New Administrator⁩**:
   - שם למשל `lancompass-reader`
   - אימות: **⁦Check Point password⁩** (או חשבון ⁦RADIUS/AD⁩ — מה ששרת
     הניהול מאמת) — או, מ־⁦R80.40⁩ ואילך, **מפתח ⁦API⁩** (אימות *⁦API Key⁩*
     של המנהל; העתיקו את המפתח כשהוא מוצג)
   - פרופיל הרשאות: הפרופיל המותאם משלב 1
   - ב־⁦MDS⁩: יוצרים אותו בתוך **הדומיין** שמיועד לסנכרון.
5. שמרו — ו־**⁦Publish⁩** (שינויי הרשאות הם אובייקטים גם כן; מנהל שלא
   פורסם לא יכול להתחבר).

⁦LanCompass⁩ מתחברת עם `read-only: true`: שרת הניהול עצמו דוחה כל שינוי
בהפעלה הזו, יהיה הפרופיל אשר יהיה.

## שלב 3 — הוכחת זמינות ידנית (אופציונלי אך מומלץ)

בדיקת שפיות של דקה לפני שנוגעים ב־⁦LanCompass⁩:

```bash
# 1. Login → session token (sid), read-only as LanCompass signs in
curl -sk https://<mgmt>/web_api/login \
  -H 'Content-Type: application/json' \
  -d '{"user":"lancompass-reader","password":"<pw>","read-only":true}'
# → {"sid":"<token>","uid":"..."}    401 כאן = אישורים או פרופיל

# 2. קריאה עם ה-sid
curl -sk https://<mgmt>/web_api/show-gateways-and-servers \
  -H 'Content-Type: application/json' -H 'X-chkp-sid: <token>' \
  -d '{"limit":5}'
# → {"objects":[...]} — אתם מוכנים.
```

ב־MDS מוסיפים `"domain":"<שם הדומיין>"` לגוף ה־login. שימו לב שה־`sid`
פג תוקף (ברירת מחדל ~10 דקות idle) — ה־connector מתחבר מחדש בכל סנכרון,
אז אין מה לנהל.

## שלב 4 — הוספת המקור ב־⁦LanCompass⁩

הגדרות → **אינטגרציות** → **מקור חדש**:

| שדה              | ערך                                                |
| ---------------- | --------------------------------------------------- |
| Kind             | `Check Point`                                       |
| שם               | למשל `HQ Check Point`                               |
| Base URL         | `https://<mgmt>` — שרת ה*ניהול*, בלי path            |
| אישורים          | user / password משלב 2 — או הפעילו **כניסה עם מפתח ⁦API⁩** והדביקו את המפתח |
| דומיין MDS       | לריבוי דומיינים בלבד — הדומיין שאליו מתחבר ה־login; ריק ב־SmartCenter יחיד |
| טבלאות runtime של ה־gateways | **כבוי** במקור חדש — קריאות זמן ריצה לכל שער דרך ה־`run-script` המאושר מראש; הפעילו רק אחרי שלפרופיל יש **⁦Run One Time Script⁩** (שלב 2) |
| הפעלה נפרדת עם הרשאת כתיבה לטבלאות זמן הריצה | **כבוי** — רק לשרת שמסרב להריץ סקריפטים בהפעלה לקריאה בלבד (בהמשך) |
| יעדי runtime     | שמות gateways מופרדים בפסיקים (אופציונלי) — ריק מתשאל את כל ה־gateways שהניהול מכיר |
| החכרות DHCP      | **כבוי** — קריאה נוספת של החכרות Gaia DHCP; רק ל־gateways שמריצים שרת Gaia DHCP (לא נפוץ) |
| מנהרות VPN       | **מופעל** — טופולוגיית קהילות VPN (ניהול) + `vpn tu tlist` לכל gateway; כתובות ה־peer הופכות לשורות `vpn-peer` |
| רישום תעודות     | **מופעל** — `cpca_client lscert` על שרת הניהול; כל תעודת ICA שהונפקה (SIC + IKE/VPN) נוחתת בדף התעודות עם תאריך התפוגה |
| לקרוא את חוקי הגישה וה־⁦NAT⁩ (פעם ביום) | **כבוי** — סמנו כדי להציג בדף של כל רשת את החוקים שנוגעים בה (בהמשך) |
| Verify TLS       | **כבוי** אם תעודת ה־Gaia היא self-signed            |
| Site / VRF       | אזור הנחיתה שייקלטו בו האובייקטים                    |
| סנכרון כל        | 0 = ידני; או למשל 60 דקות                            |

**ב־MDS (ריבוי דומיינים):** מגדירים בשדה *דומיין MDS* את הדומיין שאליו
ה־login צריך להיקשר — ה־connector מתחבר למסד הנתונים המפורסם של אותו
דומיין. (ה־scope גם ניתן ל־PATCH: `{"scope": {"domain": "<שם הדומיין>"}}`.)

ואז הלולאה הרגילה: **Test & discover** → סימון ה־scope → **Preview** של
ההפרשים → **Apply** על השורות המסומנות → ואופציונלית תזמון.

## טבלאות runtime

הדילוג השני: אחרי משיכת הניהול, ה־connector מבקש מכל gateway את הטבלאות
החיות שלו דרך ה־`run-script` של ה־Management API — הקריאה היחידה עם צורת
exec במשפחה, והיא מגודרת פעמיים:

- רשימת הפקודות המותרת מכילה את `run-script`/`show-task` לצד קריאות
  ה־`show-*` — ותו לא.
- צמד ה־`script`/`script-name` הוא רשימת היתרים *שנייה*: רק גופי הסקריפט
  המדויקים הבאים, תחת תוויות task קבועות, יכולים לרוץ אי פעם —

| מטרה        | `script`                          | רץ מתי                                |
| ----------- | -------------------------------------- | ------------------------------------- |
| טבלת ARP    | `clish -c "show arp dynamic all"`      | על כל שער וכל חבר אשכול, תמיד (כל עוד דילוג ה־runtime מופעל)   |
| החכרות DHCP | `clish -c "show dhcp server leases"`   | על כל שער וכל חבר אשכול, רק כש־*החכרות DHCP* מסומן              |
| מנהרות VPN   | `vpn tu tlist`                          | על כל שער וכל חבר אשכול, כש*מנהרות VPN* מסומן (ברירת מחדל) |
| רישום תעודות | `cpca_client lscert`                  | על שרת הניהול (`CpmiHostCkp`) פעם אחת, כש*רישום תעודות* מסומן (ברירת מחדל) |

הסקריפטים נשלחים למכונות שיכולות להריץ אותם: השערים הפשוטים וחברי
האשכול — אף פעם לא לאובייקט האשכול, שאינו מכונה.

**דילוג זמן הריצה כבוי במקור חדש.** הוא דורש את ההרשאה **⁦Run One Time
Script⁩** ברמת ⁦expert⁩ על כל שער (שלב 2), ולכן מקור ⁦Check Point⁩ חדש
מביא אובייקטים, שערים וקהילות ⁦VPN⁩ — בלי ⁦ARP⁩, ⁦DHCP⁩, מנהרות או
תעודות ⁦ICA⁩ — עד שמפעילים אותו. מקור שנוסף לפני הגרסה הזו שומר על
ההגדרה שהייתה לו.

**ההפעלה לקריאה בלבד.** כל קריאה רצה בהפעלה אחת שנפתחת עם
`read-only: true`, בשם *⁦LanCompass (read-only)⁩*, עם זמן המתנה של 600
שניות, ונסגרת בסוף הקריאה. שרת שמסרב ל־`run-script` בהפעלה לקריאה בלבד
עונה לסקריפט הראשון ב־⁦403⁩: דילוג זמן הריצה מושמט, עם הערה אחת על
הסנכרון שמציינת את שתי הדרכים לפתור — לתת לחשבון את **⁦Run One Time
Script⁩**, או לסמן **פתיחת הפעלה נפרדת עם הרשאת כתיבה לטבלאות זמן
הריצה**. עם הסימון הזה המחבר פותח הפעלה שנייה, לא לקריאה בלבד, רק
ל־`run-script` ול־`show-task`, וסוגר אותה כשהסקריפטים מסתיימים; כל קריאה
אחרת נשארת בהפעלה לקריאה בלבד.

כל ארבע הפקודות הן פקודות קריאה — פלט `show`/`vpn tu` של Gaia ורישום ה־ICA. שום דבר שהמפעיל מספק לא יכול
להגיע ל־`script` או `script-name`: ה־connector ממפה מפתח-מטרה קבוע לצמד המוצהר,
כך ששדה scope, שם אובייקט או הודעת שגיאה אף פעם לא הופכים לסקריפט.
קריאה בלבד נאכפת בקוד, לא בזהירות.

תעודה שהסנכרון יוצר היא של המקור: סנכרונים מאוחרים יותר מרעננים את תאריך
התפוגה שלה. תעודה שהזנתם או ערכתם ביד — תעודת ⁦gateway⁩ שחודשה והקלדתם את
התאריך החדש שלה — שומרת את התאריך שלכם: כשהניהול עדיין מדווח את הישן,
סקירת התוכנית מציגה התנגשות עם שני התאריכים, והתאריך של המקור נכתב רק אם
בוחרים **לקבל את זה** (ראו [של מי הערך](/he/docs/integrations/)).

הדילוג הוא **כשל-רך לכל gateway**: gateway אחד שגומר ב־timeout או שגיאה
נרשם כהערה על הסנכרון (`gw-2: run-script timeout`), לעולם לא משיכה כושלת —
gateway מת לא יכול להרעיב את האחרים. התוצאות נאספות ב־polling של tasks
(`show-task` ב־`details-level: full`, סבבים תחומים, הפלט מקודד base64) וחתוכות לתקרת שורות כמו כל סקשן אחר.

מפתחות ה־scope, להתקנות מונעות-API: `runtime` (בוליאני — המתג הראשי;
`false` במקור שנוצר עכשיו, ומקור שנשמר בלי המפתח ממשיך להריץ את הדילוג),
`runtime_rw_session` (בוליאני, ברירת מחדל `false` — ההפעלה הנפרדת עם
הרשאת כתיבה לדילוג זמן הריצה), `gateways` (רשימת שמות — מיקוד מפורש, עד
64), `dhcp` (בוליאני, ברירת מחדל `false`), `tunnels` (bool, ברירת מחדל
`true`), `certs` (bool, ברירת מחדל `true`), `policy` (בוליאני, ברירת מחדל
`false` — קריאת החוקים היומית שבהמשך), `domain` (דומיין login ב־MDS).
`certs` מכוון לשרת הניהול פעם אחת — שם חי רישום ה־ICA.

## חוקים שנוגעים ברשת

השאלה הראשונה של צוות חומת האש על רשת — אילו חוקים נוגעים בה — מקבלת
תשובה בדף של הרשת עצמה. כשבמקור מסומן **לקרוא את חוקי הגישה וה־⁦NAT⁩
(פעם ביום)**, ⁦LanCompass⁩ קוראת את המדיניות של שרת הניהול פעם ביום,
באותה הפעלה לקריאה בלבד:

- את שכבות הגישה של כל חבילת מדיניות (`show-access-rulebase`) ואת בסיס
  חוקי ה־⁦NAT⁩ שלה (`show-nat-rulebase`), בעמודים, ב־`details-level standard`
  עם מילון האובייקטים;
- את האובייקטים שהחוקים מציינים (`show-networks`, `show-hosts`,
  `show-address-ranges`, `show-groups`, `show-gateways-and-servers`), כך
  שכל קבוצה נפרשת — גם קבוצות מקוננות — וכל אובייקט הופך לכתובות שלו:
  רשת לטווח שלה, טווח כתובות לכתובת הראשונה והאחרונה, מארח או שער
  לכתובת שלו. תא שכתוב בו **⁦Any⁩** (או שהוא מוחלף בשלילה) נספר ואינו
  מוצג בשורה.

נוספות רק פקודות `show-*`; בסיס החוקים לעולם אינו נכתב (אין במחבר שום
דבר שיכול לכתוב אותו). החוקים נשמרים בטבלה לקריאה בלבד שכל קריאה מחליפה
— אין היסטוריה — והיא נמחקת יחד עם המקור כשמוחקים אותו.

**התדירות.** חוקים הם הקריאות הכבדות ביותר על שרת ניהול, ולכן הם לעולם
אינם רצים לפי לוח הזמנים של סנכרון המקור: הגדרות ← **אינטגרציות** ←
**קריאת חוקי חומת האש בכל (דקות)** — ⁦1440⁩ (פעם ביום) כברירת מחדל, ⁦0⁩ אף
פעם (ברירת המחדל באתחול: `POLICY_SYNC_MINUTES`). נקראים רק מקורות
שסומנו.

**הלוח.** בדף של רשת מוצג **חוקים שנוגעים ב־⁦10.20.1.0/24⁩** אחרי לוח
התיעוד שלה: לכל חומת אש, המספר והשם של כל חוק, השכבה שלו (או חבילת
ה־⁦NAT⁩), הפעולה שלו, איזה צד מציין את הרשת (מקור, יעד, או המקור והיעד
המקוריים והמתורגמים של ⁦NAT⁩), האובייקט (חבר בקבוצה כ־`group / member`,
עם הכתובות שלו), ומתי נקראו החוקים; ומתחת — כמה חוקים נוספים משתמשים
ב־**⁦Any⁩**. המגירה של כתובת מציגה את אותו הדבר לכתובת אחת. כל מי שמחובר
וקורא נתונים רואה את הלוח (`data:read`); ההגדרות של המחבר נשארות אצל
המנהלים. שכבות ⁦Threat Prevention⁩, ⁦HTTPS Inspection⁩ ו־⁦Application
Control⁩, ומוני הפגיעות, אינם נקראים.

## מה הוא מייבא

| נתוני Check Point                                  | אובייקט ב־⁦LanCompass⁩                     |
| -------------------------------------------------- | ------------------------------------- |
| Gateways & servers (`show-gateways-and-servers`)   | Devices (`source=integration`) — שערים פשוטים וחברי אשכול כ־*firewall* (חבר מציין את האשכול שלו), האשכול כ־*firewall-cluster*, שרת הניהול (`CpmiHostCkp`) כ־*firewall-management*; כל סוג אחר כ־*firewall* והסוג שלו נשמר |
| שדות `ipv4-address` של ה־gateways                  | Addresses — מתועדות במדיניות (`active`, אף פעם לא מסומנות כנראו) |
| אובייקטי `show-networks` (`subnet4` + mask)        | Subnets (prefixes)                    |
| אובייקטי `show-hosts` (`ipv4-address`)             | Addresses — מתועדות במדיניות: נוצרות `active`, בלי *נראה לאחרונה* ובלי ערך שנצפה; שם האובייקט ממלא רק שם מארח ריק, וכתובת שהרשת הראתה (⁦ARP⁩) שומרת את מה שהראתה |
| ARP לכל gateway (`run-script`, דילוג runtime)      | Addresses (שורות `arp`)               |
| החכרות DHCP לכל gateway (`run-script`, opt-in)     | Addresses (שורות `lease`)             |
| `vpn tu tlist` לכל gateway                     | Addresses (שורות `vpn-peer`) + פירוט מנהרות ב־provenance של הסנכרון |
| קהילות VPN (star/meshed `show-*`)              | provenance של הסנכרון — טופולוגיית המנהרות (מי מתקשר עם מי) |
| `cpca_client lscert` על הניהול                 | שורות ברישום התעודות — תעודות SIC/IKE עם תפוגה אמיתית |
| בסיסי חוקי הגישה וה־⁦NAT⁩ (לפי בחירה, פעם ביום) | לוח החוקים בדף של רשת ובמגירה של כתובת |

כל אובייקט נקרא — עד ⁦50,000⁩ מכל סוג, בעמודים עד הסך שהתשובה מציינת;
מקור שמחזיק יותר אומר זאת על הסנכרון.

שכבת ה־VPN — קהילות פלוס פירי המנהרות של כל gateway מהסנכרון האחרון — מקבלת דף משלה ב־`/vpn`: לא בתפריט; נפתח מסמל המנעול על שורת מקור Check Point בהגדרות ← אינטגרציות.

ווידג׳טים של הדשבורד מכסים את אותו השטח — מטרת **Check Point** באשף הוספת הווידג׳טים מרכזת בריאות סנכרון, רשימת שערים, פירי מנהרות (מדד, עמודות, מגמה), קהילות ותרשימי תפוגת אישורים, והכול ניזון מהכיל של הסנכרון ומרשם האישורים.

קריאה אחת עוד **נדחית למשך מתוכנן**: טבלאות הממשקים של כל gateway (VLANs +
subnets של ממשקים). מלאי הניהול בתוספת טבלאות ה־runtime שלמעלה הוא כבר רוב
מה שה־firewall יודע על הכתובות שלכם.

## הסתייגויות כנות

- **מצב מפורסם בלבד.** ה־API רואה את מסד הנתונים האחרון שפורסם. אובייקטים
  ש־admin ערך אבל לא פרסם לא יופיעו בסנכרון — ושום דבר ב־⁦LanCompass⁩ לא יכול
  לפרסם אותם (קריאה בלבד מובנית).
- **שתי-דילוגים = latency.** קריאת ARP מ־40 gateways היא 40 קריאות
  `run-script`; באסטה גדולה שמירת `sync_minutes` ≥ 15 היא הגיונית יותר מכל
  דקה.
- **סשנים סופיים.** כל סנכרון פותח הפעלה אחת לקריאה בלבד (ואת ההפעלה עם
  הרשאת הכתיבה של דילוג זמן הריצה רק כשהיא מסומנת) ומתנתק בסופו — אבל אל
  תריצו משיכות מקבילות על אותו חשבון.
- **היסחפות הרשאות.** אם אובייקטים מפסיקים להופיע בשקט, מישהו צימצם את
  הפרופיל — בדקו שוב שלב 2.

## פתרון תקלות

| סימפטום                                   | סיבה סבירה → פתרון                                    |
| ----------------------------------------- | ------------------------------------------------------ |
| Test → `unreachable`                      | Management API כבוי (שלב 1), או שה־ACL לא מאפשר את מכונת ה־⁦LanCompass⁩ |
| Test → `authentication failed`            | user/password שגוי, או שה־admin לא עבר **publish**, או דומיין שגוי (MDS) |
| שגיאת TLS verify                          | תעודת Gaia self-signed → כבו *Verify TLS*              |
| Test תקין אבל אפס אובייקטים               | אובייקטים קיימים רק כשינויים לא מפורסמים; או לפרופיל אין הרשאות קריאה |
| שורות ARP של gateway חסרות                | ה־`run-script` רשם הערה לכל gateway על הסנכרון (timeout, או `show arp` לא נתמך בגרסת ה־Gaia הזו) — בדקו את גרסת ה־Gaia וגישת ה־API של ה־gateway; שאר המשיכה נקלטה |
| הכל מיושן אחרי דחיפת policy                | נורמלי — הסנכרון רואה מצב מפורסם; חכו לסנכרון הבא או הריצו Apply |

## הערות אבטחה

- האישורים שמורים מוצפנים ב־`cred_enc` (AES-256-GCM); ה־API מחזיר רק
  `cred_set`, לעולם לא את הסוד עצמו.
- המקור הוא LAN-side בעיצובו — ⁦LanCompass⁩ יוזם קריאות ל־controller, שום דבר
  לא נכנס. שמרו על ה־ACL של ה־Management API הדוק בכל מקרה.
- שורות `integration` יושבות באמצע סדר העדיפות: מעל תצפיות scan/SNMP, מתחת
  לנתוני manual/import. התנגשויות מדווחות ב־preview ובשורת `N conflicts
  skipped` של המקור — אף פעם לא מיושמות בשקט.
