# שרת גיבוי חם

אפשר לשמור במארח נוסף עותק משוכפל של ⁦PostgreSQL 16⁩. הקידום **ידני**:
אין מעבר אוטומטי ואין אשכול. התקנה שלא מצטרפת אינה משתנה והניטור כבוי
כברירת מחדל. החבילה הלא מקוונת כוללת קובץ שכפול, ערכה ומדריכים מלאים
באנגלית ובעברית.

## התקנה ואימות

פעלו לפי ⁦deploy/standby/RUNBOOK.he.md⁩. הגדירו סיסמת שכפול חזקה באמצעות
⁦LANCOMPASS_REPLICATION_PASSWORD⁩ או קובץ הסוד שלו ובחרו כתובת ממשק
ייעודי במשתנה ⁦LANCOMPASS_REPLICATION_BIND⁩. **המפתח האפקטיבי
⁦LANCOMPASS_SECRET_KEY⁩ חייב להיות זהה בשני המארחים.** העתיקו בנפרד
פרטי מסד נתונים, תמונות, החרגות סריקה והגדרות התחברות וקבצים מקומיים.
התעבורה מאומתת אך **אינה מוצפנת**. השתמשו ברשת ⁦VLAN⁩ ייעודית או במנהרה
וצמצמו את כלל הגישה לכתובת העותק.

בראשי משתמשים גם בקובץ השכפול:

```sh
docker compose -f docker-compose.yml -f docker-compose.primary.yml up -d
docker compose -f docker-compose.yml -f docker-compose.primary.yml exec -T api \
  python -m app.cli standby enable-primary
docker compose -f docker-compose.yml -f docker-compose.primary.yml exec -T api \
  python -m app.cli standby status
```

במארח השני, בתיקיית ⁦deploy/standby/⁩, מגדירים את ⁦LANCOMPASS_PRIMARY_HOST⁩
ומפעילים את הערכה. רק מסד העותק מתחיל. בכרך ריק נלקח גיבוי בסיס; כרך
תקין קיים נשמר. בדיקת מצב אינה מחייבת הפעלת ממשק או סורק:

```sh
docker compose up -d
docker compose --profile failover run --rm --no-deps api \
  python -m app.cli standby status
```

בודקים תפקיד, זרימה, חריץ פעיל ⁦lancompass_standby⁩, פיגור ניגון וכמות
⁦WAL⁩ מול המכסה (ברירת מחדל ⁦8GB⁩). תוצאת פענוח ⁦mismatch⁩ מחזירה
קוד ⁦1⁩ ומחייבת תיקון מפתח. התוצאה ⁦no credentials⁩ מציינת שאין
אישור מוצפן לבדיקה. נבדק אישור אחד לקריאה בלבד, בלי להציג את ערכו.

## ניטור

בהגדרות ← גיבוי מפעילים ציפייה לעותק. סף הפיגור הוא ⁦30–86400⁩ שניות,
ברירת מחדל ⁦300⁩. העובד בראשי בודק בכל דקה. מנתבים ⁦standby.*⁩
לערוץ התראות. נתק, פיגור גבוה ו־⁦WAL⁩ מעל ⁦75%⁩ מהמכסה מתריעים
רק במעבר מצב; חזרה לתקינות מתריעה כשכל התנאים חלפו. הכרטיס מתרענן
בכל דקה. עותק ללא נתונים ממתינים מציג פיגור אפס; פיגור לא ידוע אינו אפס.

ראשי כבוי לחלוטין אינו יכול לשלוח התראות בעצמו. נדרש ניטור מארח חיצוני.
כיבוי הציפייה אינו מפסיק שכפול ואינו מסיר את החריץ ששומר ⁦WAL⁩.

## מעבר וחזרה

אם הראשי נגיש עוצרים **את כל המחסנית, כולל הסורק, קודם**. אם אינו
נגיש, אדם חייב לוודא שהוא מבודד או מגודר ולא יוכל לחזור לסרוק או לקבל
כתיבות. אין להפעיל שני סורקים. בודקים ניגון ופענוח ואז:

```sh
docker compose --profile failover run --rm --no-deps api \
  python -m app.cli standby promote
docker compose --profile failover up -d
```

פקודת הקידום נדחית בראשי ולעולם אינה מפעילה מכולות. הפקודה הנפרדת
מפעילה ⁦Redis⁩, ⁦API⁩, סורק וממשק. מפנים משתמשים ובודקים התחברות,
אישור שמור וכתיבה רגילה.

שכפול אסינכרוני עלול לאבד כתיבות שטרם נוגנו. מושבי התחברות ומשימות
בתור ⁦Redis⁩ אובדים: המשתמשים מתחברים מחדש, משימות ידניות נבדקות או
מופעלות שוב ומשימות מתוזמנות חוזרות עם אפשרות לכפילויות. קבצי מארח
משוחזרים בנפרד. ממשיכים לגבות את הראשי.

בחזרה בונים במארח הישן עותק עם **כרך חדש וריק** מהראשי שקודם. שומרים
את הכרך הישן לחקירה; לא מפעילים אותו כראשי נוסף ולא ממזגים כתיבות.
מעבר מתוכנן נוסף משתמש באותו תהליך ידני. המדריך מסביר כיצד לפתוח
באופן מאובטח את יציאת השכפול של ערכה שקודמה.

כשעותק הוסר לצמיתות, עוצרים אותו ומפעילים בראשי
⁦standby drop-slot --yes-drop-slot⁩. הדגל חובה וחריץ פעיל נדחה.
מכבים ציפייה אם אין תחליף מתוכנן. חריץ שנפסל מחייב גיבוי בסיס חדש.
