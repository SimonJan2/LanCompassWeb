# אינטגרציות

סריקה לומדת מה עונה ל־ARP בסגמנט המקומי. **אינטגרציות** גורמות
ל־controllers שלכם *לדווח על עצמם*: firewall כבר מכיר את הממשקים, ה־VLANs,
החכרות ה־DHCP וטבלת ה־ARP שלו — כולל לקוחות בסגמנטים מרותזים שסריקה
מקומית לא יכולה להגיע אליהם; hypervisor מכיר את ה־guests שלו ואת מיפוי
ה־NIC→IP שלהם. מקור הוא ערוץ תצפית שני לאותו מנוע reconcile.

כל ה־connectors הם **לקריאה בלבד**: ⁦LanCompass⁩ לעולם לא מקצה, לא דוחף ולא
משנה חוק. קריאה-בלבד באה בשלוש צורות, כל אחת נאכפת בקוד: `GET` טהור
(OPNsense, Proxmox, FortiGate, UniFi, MikroTik, PAN-OS, NetBox); POST אחד
של לחיצת יד לאימות ואחריו GETים (vCenter, Omada); או שכבת RPC-מעל-POST
מוגבלת מבנית לרשימה מוצהרת (פקודות `show-*` של Check Point, פעולות
`show …` של PAN-OS, `v3/*/list` של Nutanix).

## ה־connectors

| Kind              | Credentials              | קורא                                                  |
| ----------------- | ------------------------ | ---------------------------------------------------- |
| **OPNsense**      | API key + secret         | ממשקים, VLANs, subnets, החכרות/טווחי DHCP, ARP, מכשיר ה־firewall |
| **Check Point**   | user + password          | Gateways & servers, אובייקטי רשת (subnets), אובייקטי host — מצב הניהול המפורסם |
| **vCenter / ESXi**| user + password          | Hosts, VMs מקושרים תחתיהם, IPs של guests (מותנה ב־Tools) |
| **Proxmox VE**    | מזהה API token + secret  | Nodes של ה־cluster, guests מסוג QEMU/LXC, VLANs/SVIs של bridges, IPs של guests |
| **FortiGate**     | API token                | VDOMים, ממשקים/VLANים, subnets, השכרות DHCP, ARP, מלאי מכשירים |
| **PAN-OS**        | API key                  | אובייקטי כתובות מותחמי־vsys, ממשקים, הגדרות DHCP, ARP, השכרות חיות |
| **Nutanix Prism** | user + password          | אשכולות, hosts של AHV, VMs מקושרים תחתיהם, subnets, pools של IP |
| **UniFi**         | API key                  | אתרים, רשתות/VLANים, מכשירים (APים→wifi), לקוחות        |
| **Omada**         | client ID + secret       | אתרים, רשתות LAN, מכשירים, לקוחות                      |
| **MikroTik**      | user + password          | ממשקים, VLANים, SVIs, pools/השכרות DHCP, ARP          |
| **Active Directory** | bind קריאה־בלבד (או אנונימי) | מחשבים → מכשירים, Sites & Services → אתרים/subnets, אזורי DNS משולבי AD ו־PTR → שמות מחשב |
| **NetBox**        | API token                | אתרים, מכשירים, prefixes (subnets), כתובות IP — שיקוף חי |
| **Windows DHCP**  | אין — השרת מעלה את קובץ הייצוא שלו | טווחים → subnets וטווחי DHCP, הקצאות שמורות, החכרות (IPv4 ו־IPv6) |

Guests מ־connectors של compute מיובאים כ־devices עם `family=compute`,
מקושרים תחת ה־hypervisor שלהם דרך `host_device_id` — תצוגת ה־device מראה
hosts עם ה־VMs מקוננים מתחתם.

## הזרימה

הגדרות → **אינטגרציות** → **מקור חדש**. מזינים את כתובת ה־controller
ואת ה־credentials, ואז:

1. **בדיקה וגילוי** — בדיקה חיה: זמינות, זהות ה־controller (מוצר, גרסה,
   hostname) וספירות של מה שהוא רואה.
2. **סימון הסקופ** — אילו מערכי נתונים (VLANs, רשתות משנה, טווחי DHCP,
   כתובות, devices) ואילו *דברים* לקרוא — השם משתנה בין kinds: ממשקים ב־
   OPNsense וב־MikroTik, nodes ב־Proxmox, VDOMים ב־FortiGate, מערכות
   וירטואליות ב־PAN-OS, אשכולות ב־Nutanix, אתרים ב־UniFi וב־Omada. הסקופ
   נשמר וחל גם על סנכרונים מתוזמנים.
3. **תצוגה מקדימה** — diff יבש: כל אובייקט שנצפה מסווג כ־*יצירה*,
   *עדכון*, *קיים*, *התנגשות*, *דילוג* או *שגיאה*, עם diff ברמת שדה
   כשמשהו היה משתנה. שום דבר לא נכתב.
4. **החלה** — השורות המסומנות נכתבות בטרנזקציה אחת. ההחלה שולפת מחדש
   מן ה־controller ולא מנגנת את התצוגה המקדימה, אז לעולם לא שולבים
   נתונים מיושנים.

כל החלה — ידנית או מתוזמנת — רושמת import batch לצורך מוצא; רשימת
**הסנכרונים האחרונים** של המקור מציגה אותם.

### תצוגות מקדימות ארוכות

תצוגה מקדימה, החלה או *בדיקה* של ספרייה גדולה או של ⁦vCenter⁩ יכולות
לקחת דקה או שתיים — אלפי מחשבים או מכונות וירטואליות נקראים עמוד אחר
עמוד. הדף מחכה להן (עד עשר דקות), ואחרי 10 שניות מופיעה מתחת לכפתור
שורה שאומרת זאת: *עדיין קוראים מ־… — ספרייה גדולה או ⁦vCenter⁩ לוקחים
דקה או שתיים.* החיפוש בקבוצות של הספרייה בהגדרות ← חשבון ואבטחה מציג את
אותה שורה. **תצוגה מקדימה** של ⁦Active Directory⁩ קוראת מדגם של 64 שמות
⁦reverse DNS⁩ מתוך החלון שסנכרון קורא; **החלה** והתזמון עדיין קוראים את
כל החלון (512 בכל סנכרון), כך שתצוגה מקדימה אחרי ייבוא של חוברת גדולה
נשארת מהירה, וסנכרון עדיין ממלא כל שם.

## OPNsense

ה־connector של הייחוס קורא את ה־REST API של OPNsense
(`/api/core/system/status`, `/api/interfaces/overview`, ARP של
diagnostics וחכרות DHCPv4) — בקשות GET בלבד.

**ה־credentials** הם צמד API key/secret: System → Access → Users →
בוחרים (או יוצרים) משתמש → *API keys* → ה-+ מייצר מפתח ומוריד את
ה־secret. משתמש עם הרשאת קריאה-בלבד הוא כל מה ש־⁦LanCompass⁩ צריך — הוא
לעולם לא קורא לנקודת קצה כתיבה. המפתח הולך לשדה **API key**, ה־secret
לשדה **API secret**.

**מה הוא מייבא:**

| נתון מה־controller                          | אובייקט ⁦LanCompass⁩                    |
| ------------------------------------------- | ----------------------------------- |
| ממשקים עם תגי VLAN                           | VLANs                               |
| הקצאות subnet של ממשקים                      | רשתות משנה (prefixes)               |
| טווחי DHCPv4                                 | טווחי IP                            |
| חכרות DHCPv4, רשומות ARP                     | כתובות (`source=integration`)       |
| ה־firewall עצמו                              | מכשיר (`source=integration`)        |

ריזרבציות DHCP מיובאות כ־`reserved`; חכרות רגילות ורשומות ARP כ־
`discovered`. שורות שה־connector מדווח מוטבעות ב־`source: integration` —
משתמשים בפאסט המקור ברשימת הכתובות כדי לסנן אותן.

*שכבת קהילה — ממשיכים לעבוד, בלי קריאות חדשות (יחד עם ⁦UniFi⁩, ⁦Omada⁩ ו־⁦MikroTik⁩).*

### תפקיד לקריאה בלבד

*לא נבדק מול מכשיר בגרסה הזו (שכבת קהילה); שמות ההרשאות הם של ⁦OPNsense 25.x⁩.*

1. *⁦System⁩* ← *⁦Access⁩* ← *⁦Groups⁩* ← *⁦Add⁩*: צרו את `lancompass-ro` עם ההרשאות האלה בלבד: **⁦Lobby: Dashboard⁩**, **⁦Status: Interfaces⁩**, **⁦Status: DHCP leases⁩**, **⁦Diagnostics: ARP Table⁩**, **⁦Diagnostics: NDP Table⁩**.
2. *⁦System⁩* ← *⁦Access⁩* ← *⁦Users⁩* ← *⁦Add⁩*: צרו את `lancompass`, חבר רק ב־`lancompass-ro`, בלי מעטפת, עם סיסמה ארוכה ואקראית שאף אחד לא מתחבר איתה.
3. אצל המשתמש הזה, *⁦API keys⁩* ← `+`: ⁦OPNsense⁩ מוריד את המפתח ואת הסוד פעם אחת. הדביקו את המפתח בשדה **⁦API key⁩** ואת הסוד בשדה **⁦API secret⁩**.

**מה ⁦LanCompass⁩ קוראת:** `/api/core/system/status`, `/api/interfaces/overview`, `/api/dhcpv4/leases`, `/api/diagnostics/interface/getArp` ו־`getNdp` — ⁦GET⁩ בלבד.

### מה כל הודעה אומרת

| הודעה | מה היא אומרת ← מה עושים |
|---|---|
| *…: האימות נכשל (401)* | המפתח או הסוד שגויים, או שנמחקו ← צרו מפתח חדש אצל המשתמש |
| *…: האימות נכשל (403)* | לקבוצה של המשתמש חסרה ההרשאה של הקריאה ← הוסיפו אותה ל־`lancompass-ro` (*בדיקת חיבור* מציינת את הקריאה) |
| *…: לא נמצא* | בגרסה הזו של ⁦OPNsense⁩ אין אף אחד מהנתיבים של הקריאה ← עדכנו את ⁦OPNsense⁩; שאר הקריאות ממשיכות להסתנכרן |
| *…: הבקשה לא נענתה בזמן* | חומת האש לא עונה מ־⁦LanCompass⁩ ← בדקו את הניתוב ואת הממשקים שממשק הניהול מאזין עליהם |
| *אף נקודת קצה לא ענתה* | אף קריאה לא ענתה ← בדקו את כתובת הבסיס ואת התעודה (ראו *תעודות*) |

## NetBox

ה־connector של NetBox הוא אחי ה**שיקוף החי** של
[ייבוא קובץ NetBox](/he/docs/import/): בקשות `GET` מאומתות־אסימון מול
`/api/dcim/sites/`, ‏`/dcim/devices/`, ‏`/ipam/prefixes/` ו־
`/ipam/ip-addresses/` — התעבורה לא יכולה לשלוח שאינו־GET, ולכן גם אסימון
עם הרשאות כתיבה לא יכול לכתוב דרכו. מריצים את ⁦LanCompass⁩ לצד NetBox פעיל
להערכה או לביקורת; כשמגיע יום המעבר, ייבוא הקובץ החד־פעמי הוא החצי השני
של הסיפור.

הסקופ רוכב על מסנני שאילתה: **VRF של NetBox** (שם, RD או id → `?vrf=`),
**‏slug אתר** בתוספת רשימת סימון האתרים (→ `?site=` על prefixes; מכשירים
וכתובות IP מיוחסים בצד־לקוח דרך מפת המכשירים), ו**סטטוס אובייקט**
(`?status=` על prefixes/כתובות, ברירת־מחדל `active`). המשיכות חסומות —
עמודים של 500 שורות, 40 עמודים לנקודת קצה — ונקודת קצה שנכשלת רושמת
שגיאה ונותנת לשאר המשיכה להסתיים. המדריך הייעודי:
**[NetBox](/he/docs/netbox/)**.

## ⁦Windows DHCP⁩

⁦LanCompass⁩ קורא את ⁦Windows DHCP⁩ מ**הקובץ שהשרת מייצא** — הוא לא מדבר
עם שרת ה־⁦DHCP⁩ באף פרוטוקול של ⁦Windows⁩ ולא צריך עליו שום הרשאה. משימה
מתוזמנת בשרת מריצה `Export-DhcpServer -Leases` (קובץ ⁦XML⁩ אחד של כל טווחי
⁦IPv4⁩ ו־⁦IPv6⁩, ההקצאות השמורות וההחכרות שלהם) ושולחת את הקובץ למקור עם
אסימון ⁦API⁩ שלא יכול לעשות שום דבר אחר.

1. **הוסיפו את המקור.** הגדרות ← אינטגרציות ← *הוספת מקור*, סוג
   **⁦Windows DHCP⁩**. הכתובת היא `upload://` ושם השרת
   (`upload://dhcp01.corp.example`) — תווית בלבד, אין אליה חיוג. *להתריע
   כשקובץ הייצוא ישן מ־* קובע כמה ישן יכול הקובץ החדש ביותר להיות (36 שעות
   כברירת מחדל) לפני שסנכרון אומר זאת.
2. **הנפיקו את האסימון.** הגדרות ← אסימוני ⁦API⁩: אסימון עם ההרשאה
   **העלאת קובץ ייצוא של מקור** (`sources:upload`) ותו לא. הוא יכול לשלוח
   את הקובץ הזה ונדחה בכל מקום אחר, כולל `/sources`.
3. **העתיקו את שתי השורות.** שלב *פרטי ההתחברות* של המקור מציג אותן תחת
   *הריצו בשרת ה־⁦DHCP⁩ כמשימה מתוזמנת*; הדביקו את האסימון כדי להשלים
   אותן (הוא לא נשמר), והוסיפו אותן כמשימה מתוזמנת בשרת ה־⁦DHCP⁩, לפחות
   פעם ביום:

   ```powershell
   Export-DhcpServer -File "$env:ProgramData\lancompass-dhcp-export.xml" -Leases -Force
   Invoke-RestMethod -Method Post -Uri "https://lancompass.example/api/v1/source-uploads/12" -Headers @{ Authorization = "Bearer ipam_…" } -InFile "$env:ProgramData\lancompass-dhcp-export.xml" -ContentType "application/xml"
   ```

4. **בדיקה** קוראת את הקובץ החדש ביותר ומדווחת על הטווחים, ההקצאות
   השמורות, ההחכרות והגיל שלו; **תצוגה מקדימה** ו**החלה** מריצות את
   התוכנית הרגילה.

מה נכנס, דרך אותה תוכנית כמו כל מקור:

- כל **טווח ⁦IPv4⁩** ← רשת (`ScopeId` / `SubnetMask`, השם שלו, אפשרות 3
  כשער) וה־pool שלו (`StartRange`–`EndRange`) כטווח ⁦DHCP⁩; כל **טווח
  ⁦IPv6⁩** ← ה־⁦/64⁩ שלו;
- כל **הקצאה שמורה** ← כתובת שמורה עם השם שלה (מזהה הלקוח כ־⁦MAC⁩ כשהוא
  כזה);
- כל **החכרה** ← כתובת עם ה־`HostName` ומזהה הלקוח שלה (⁦IPv4⁩ ו־⁦IPv6⁩).
  החכרה *⁦Declined⁩* — הסימן `BAD_ADDRESS` של השרת — אינה לקוח ונשארת
  בחוץ.

**העלאות.** עד ⁨50⁩ ⁦MB⁩, נבדק תוך כדי שהקובץ מגיע. ההעלאה החדשה ביותר
וזו שלפניה נשמרות בכרך הגיבויים (`<backup dir>/sources/<id>/`); השלישית
מוחקת את הישנה ביותר. קובץ שיש בו `<!DOCTYPE` — שלעולם אינו חלק מקובץ
ייצוא, וכך הייתה מגיעה מתקפת ישויות ⁦XML⁩ — נדחה לפני שהוא נקרא, וכך גם כל
קובץ שאינו קובץ ייצוא של ⁦DHCP⁩.

**כשהמשימה נעצרת.** סנכרון שקובץ הייצוא החדש ביותר שלו ישן מהקו של המקור
הוא **חלקי**: מצב המקור אומר *„קובץ הייצוא של ⁦DHCP⁩ בן יומיים — בדקו את
המשימה המתוזמנת ב־⁨dhcp01⁩”*, וגם סקירת התוכנית אומרת זאת. הנתונים ישנים
כמו קובץ הייצוא האחרון — זה המחיר של אי־הצורך בפרוטוקול של ⁦Windows⁩
ובהרשאה בשרת.

## של מי הערך

מקור משנה רק את מה ששלו. מכשיר, כתובת, ⁦VLAN⁩, רשת משנה, אתר או תעודה הם
**של המקור הזה** כל עוד הסנכרון שלו יצר אותם ואיש לא שינה אותם מאז; עריכה
שלכם בשדה כלשהו בשורה כזו הופכת אותה **לשלכם**, ותעודה שחודשה שומרת את
התאריך שהקלדתם. העמודה **בעלים** בסקירת התוכנית אומרת של מי הערכים שכל
שורה תשנה: *שלך*, *ייבוא*, *המקור הזה*, *מקור אחר: שם* או *סריקה*.

| המקור היה… | בשורה של המקור הזה | בשורה של כל אחד אחר |
| --- | --- | --- |
| יוצר שורה | מוחל | — |
| משנה ערך | מוחל | **התנגשות** שממתינה לכם |
| ממלא שדה ריק (שער, אתר, תיאור, דגם או מספר סידורי של מכשיר, המכשיר שכתובת שייכת אליו) | מוחל | **התנגשות**: "למלא את ⁦gateway⁩ בערך ⁦10.0.0.1⁩?" |
| מרענן תאריך תפוגה של תעודה | מוחל | **התנגשות** שמציגה את שני התאריכים |

שורת התנגשות (אדומה) לעולם לא מוחלת מעצמה. בסקירת התוכנית כל אחת מציעה
**להשאיר את שלי** (ברירת המחדל — הערך שלכם נשאר) ו**לקבל את זה** (ההחלה הזו
כותבת את הערך של המקור בשורה הזו בלבד). גם בהתנגשות הסנכרון רושם את מה
שהמקור ראה — כתובת שומרת את ה־⁦MAC⁩ ושם המארח שלכם, בעוד הערכים שנצפו
ו־*נראה לאחרונה* מתעדכנים.

רשתות משנה מקוננות מתוכננות בבטחה: רשת שמכילה אחרות נוצרת **כמכולה**,
ורשת שהייתה יושבת בתוך אחת הרשתות שלכם שאינה מכולה ממתינה עם ההודעה "בתוך
⁦10.0.0.0/16⁩, שאינה מכולה — הפכו את ⁦10.0.0.0/16⁩ למכולה כדי לשמור את
שתיהן". התוכנית לעולם לא מגיעה למסד הנתונים עם חפיפה, כך שרשת משנה חריגה
אחת כבר לא מכשילה כל סנכרון שאחריה.

## אובייקט אחד, שורה אחת

כל מקור שומר רשימה של האובייקטים שראה, כל אחד לפי המזהה של הספק עצמו —
‏⁦objectGUID⁩ של מחשב ב־Active Directory, מזהה ה־VM ב־vCenter
(‏⁦vm-1007⁩), ה־vmid של אורח ב־Proxmox, ה־extId של Nutanix, המזהה של
NetBox, ה־uid של Check Point, ו־⁦<vdom|vsys>/<name>⁩ של FortiGate ו־PAN-OS
— אף פעם לא שם. הרשימה הזו היא מה שמאפשר את אלה:

| מה קורה במקור | מה ⁦LanCompass⁩ עושה |
| --- | --- |
| אובייקט **שינה את שמו** | אותה שורה מקבלת את השם החדש (בשורה שהמקור הוא הבעלים שלה; בשורה של כל אחד אחר שינוי השם ממתין: "שם שונה ב־vCenter: ישן ← חדש"). אף פעם לא מכשיר שני. |
| אובייקט **נמחק** | אחרי תשובה מלאה (תקינות **תקין**) הוא מסומן **לא נמצא עוד** — אף פעם לא אחרי תשובה חלקית, מוחזקת או שנכשלה. סנכרון מתוזמן אינו מוחק ואינו מוציא משימוש דבר. |
| ‏VM **עובר** למארח אחר | הקישור למארח עוקב אחרי המארח שהוא רץ עליו (במכשיר של מישהו אחר המעבר ממתין: "הועבר ב־vCenter אל ⁦esx-2⁩"). |
| שני מקורות נותנים שם **לכתובת אחת** | השם שייך למקור שהסנכרון שלו יצר את הכתובת; השם של מקור אחר נרשם רק כמה שנצפה (*נצפה*). תשובת ⁦PTR⁩ של DNS לעולם לא דורסת שם שנתנו חומת אש או אדם. |
| שני **תחומי ניתוב** מחזיקים אותה רשת משנה | כל אחד נכנס לטבלת ה־⁦VRF⁩ שמיפיתם אליה (ראו [NetBox](/he/docs/netbox/)) — אף פעם לא מתמזגים. |

מכשירים מותאמים קודם לפי המזהה של המקור עצמו, אחר כך לפי ⁦MAC⁩, מספר
סידורי, השם המלא, ושם המארח הקצר רק כשלאחד משני השמות אין דומיין —
‏⁦ws-1.branch⁩ לעולם אינו ⁦ws-1.corp⁩. כתובות מותאמות לפי ⁦VRF⁩ + כתובת,
‏VLANs לפי VID ורשתות משנה לפי CIDR.

**אובייקטים שלא נמצאים עוד** ממתינים לכם בסקירת התוכנית, במקטע **לא נמצא
עוד ב־vCenter** (שם המקור): **להוציא משימוש** (מכשיר יוצא משימוש, כתובת
מסומנת לא מקוונת) או **להשאיר** (הוא נשאר, ומפסיק לשאול עד שייעלם שוב).
אובייקט שלא נמצא עוד אומר זאת בעמוד שלו — "לא נמצא עוד ב־vCenter מאז
27.10.2026" — ומכשיר מראה מתי כל מקור ראה אותו לאחרונה ("נראה על ידי vCenter
לפני 3 דק׳"). אובייקט שחוזר מנקה את הסימון. מחיקת מקור מוחקת את הרשימה שלו,
אף פעם לא את האובייקטים שיצר.

## כששני מקורות רואים מכונה אחת

מכונה וירטואלית מוכרת לרוב פעמיים: ⁦vCenter⁩ מחזיק אותה לפי מזהה המכונה
וכרטיסי הרשת שלה, ⁦Active Directory⁩ לפי אובייקט המחשב וה־`dNSHostName`
שלו. כל סנכרון שומר על הסדר שלו (המזהה במקור, אחר כך ⁦MAC⁩, מספר סידורי
ושם) ולעולם לא מחבר בעצמו שורה לאובייקט של מקור אחר.

- **הדומיין אינו שינוי שם.** כשמכשיר שמקור אחר מחזיק לפי מזהה הספק נקרא
  `srv-app-02` והמקור הזה קורא לאותו אובייקט `srv-app-02.lab.test`, התוכנית
  אומרת *קיים* — לא התנגשות *שינוי שם* בכל סנכרון. חלק מארח אחר הוא עדיין
  שינוי שם שאדם מחליט עליו.
- **חכירות הן ראיה.** כשסנכרון של ⁦FortiGate⁩ או של ⁦Windows DHCP⁩ מוחל, ה־⁦MAC⁩,
  שם המארח ומזהה הלקוח של כל חכירה נשמרים כראיית `lease` של הכתובת
  (תצוגה מקדימה לא כותבת אף אחת), כך שהזהות והשם שהרשת נותנת למארח
  מגיעים ממה ששרת ה־⁦DHCP⁩ יודע.
- **המתאים מחבר את השאר — כהצעות.** אחרי כל סנכרון המתאים מחפש כתובות
  שהן מכשיר של מקור, כמה כתובות של מכונה אחת ומכשירים שהם אחד; כל חיבור
  הוא הצעה בתיבת הגילויים (*קישור*, *לא אותו מכשיר…*), שלעולם לא מוחלת
  מעצמה. ראו [מארח אחד, הרבה מקורות](/he/docs/discovery/#מארח-אחד-הרבה-מקורות).

## Credentials וסודות

שדות ה־credential הם **write-only**: הצמד מוצפן במנוחה (AES-256-GCM תחת
מפתח-האב של השרת) לתוך `cred_enc`, התשובות מדווחות רק `cred_set`,
והטקסט הגלוי לעולם לא מופיע בלוגים, שורות plan או הודעות שגיאה. משאירים
את שני השדות ריקים בעריכה כדי לשמור את הצמד השמור; שולחים credential
ריק כדי לנקות אותו.

## תעודות

כל מקור ⁦HTTPS⁩ בודק את התעודה של השרת לפני שפרטי ההתחברות עוברים בחיבור, גם ב־⁦worker⁩ וגם באתר:

- **אימות תעודת ⁦TLS⁩** פעיל, בלי שום דבר נוסף: מאגר האמון של המערכת — מספיק לתעודה ציבורית.
- **תעודת ⁦CA⁩ (⁦PEM⁩)**: ה־⁦CA⁩ הפנימי או בחתימה עצמית שהתעודה של המכשיר נשענת עליו — תעודה אחת או כמה. השם של המכשיר עצמו נבדק, אף ש־⁦LanCompass⁩ מתחברת לכתובת שהשם פוענח אליה.
- **הצמדת תעודה (⁦SHA-256⁩)**: התעודה הזו בדיוק, ונדחית כל תעודה אחרת שהשרת מציג — גם כזו ש־⁦CA⁩ מהימן חתם. *בדיקת חיבור* מציגה את התעודה שהשרת הציג (נושא, מנפיק, תוקף, שמות, ⁦SHA-256⁩): השוו את טביעת האצבע למסוף של המכשיר, ואז **לסמוך על התעודה הזו** מצמיד אותה בלחיצה אחת.
- **אימות תעודת ⁦TLS⁩** כבוי: מותר, וכל תצוגה של המקור אומרת שהסיסמה עוברת בחיבור שלא אומת. ⁦PEM⁩ או הצמדה מחזירים את האימות.

### החלפת ⁦CA⁩

1. לפני ההחלפה, הדביקו את ה־⁦CA⁩ החדש מתחת לישן בשדה **תעודת ⁦CA⁩ (⁦PEM⁩)** של המקור: שניהם מהימנים בזמן שהתעודות של המכשירים מונפקות מחדש.
2. הנפיקו מחדש את התעודה של כל מכשיר מה־⁦CA⁩ החדש, והריצו *בדיקת חיבור* על המקור שלו.
3. כשכל מכשיר עונה בתעודה מה־⁦CA⁩ החדש, הסירו את ה־⁦CA⁩ הישן מהשדה.
4. מקור מוצמד דוחה את התעודה שהונפקה מחדש: פתחו את *בדיקת חיבור*, השוו את טביעת האצבע החדשה למסוף של המכשיר וסמכו עליה שוב.

לעולם אל תכבו את האימות כדי לעבור החלפה.

## דרישות רשת

- `base_url` חייב להיות `http`/`https` — כתובת IP מילולית או שם
  בר-resolve. סכמות אחרות נדחות מיד.
- ה־host עובר resolve פעם אחת כשסנכרון מתחיל והסשן נעצב לאותה כתובת —
  DNS rebind באמצע הסנכרון לא יכול להפנות את הבקשה.
- תעודות self-signed הן הנורמה על controllers: מכבים את **אימות תעודת
  TLS** אם שלכם כזו. לשימוש מקומי ב־LAN בלבד.
- כתובות פרטיות (⁦RFC 1918⁩) ו־⁦ULA⁩ הן המקום שבו המקורות חיים, והן תמיד
  מותרות. ⁦loopback⁩ (⁦localhost⁩, ⁦127.0.0.1⁩), כתובות ⁦link-local⁩,
  שירותי ה־⁦metadata⁩ של ענן (⁦169.254.169.254⁩, ⁦fd00:ec2::254⁩)
  והכתובת והפורט של ההתקנה הזו עצמה (**כתובת ציבורית (⁦URL⁩)** בהגדרות ←
  תכונות) נדחים — כששומרים את המקור, ושוב בכתובת שהשם שלו מתורגם אליה בכל
  סנכרון — אלא אם מנהל מסמן במקור הזה **לאפשר כתובת פנימית (⁦loopback⁩ או
  ⁦link-local⁩)**. מקור שנדחה אומר למה: "הכתובת הזו נמצאת בהתקנה עצמה, היא
  ⁦link-local⁩ או שירות ⁦metadata⁩ — סמנו “לאפשר כתובת פנימית” כדי להשתמש
  בה".
- הערת air-gap: connectors מבצעים polling ל־controller ישירות — שום דבר
  לא יוצא מה־LAN. controller שלא נגיש ממכונת ה־⁦LanCompass⁩ פשוט לא יכול
  להסתנכרן.

## סנכרון מתוזמן

מגדירים **סנכרון כל (דקות)** על המקור (`0` = ידני בלבד) ומפעילים את
מתג **הפעלת סנכרון מקורות מתוזמן** הגלובלי. ה־tick של ה־worker מדי דקה
מוצא מקורות שהמרווח שלהם עבר ומריץ את *אותו* נתיב מיזוג כמו החלה ידנית —
התנגשויות עדיין מדולגות ונספרות לשורת השגיאה האחרונה של המקור ("N
התנגשויות ממתינות לאדם"), לעולם לא מנוחשים אוטומטית. מקור שנכשל רושם את
השגיאה שלו ולא מנסים אותו שוב עד המרווח הבא.

**מה סנכרון מתוזמן מחיל** (כרטיס התזמון, `SOURCES_AUTO_APPLY` בקובץ
`.env`): *שורות חדשות והשורות של המקור* — ברירת המחדל — מחיל יצירות ושינויים
בשורות שהמקור הוא הבעלים שלהן (ראו **של מי הערך**); כל שינוי אחר ממתין
לכם. *כלום — כל סנכרון ממתין לאדם* שומר במקום זה כל תוכנית מתוזמנת: המקור
מוצג *מוחזק — ממתין לאדם* ואתם מחילים אותה מסקירת התוכנית.

### שורות חדשות מתזמון

**מה תזמון עושה עם מחשבים ומכונות וירטואליות חדשים** (כרטיס התזמון;
`SOURCES_SCHEDULE_CREATES` בקובץ `.env` הוא תיעוד בלבד): *הצעה בתור הגילוי* —
ברירת המחדל — משאירה מחוץ למלאי את המחשבים החדשים (Active Directory)
ואת המכונות הווירטואליות החדשות (vCenter, Proxmox, Nutanix) של סנכרון מתוזמן:
כל אחד ממתין ב[גילוי](/he/docs/discovery/#בוקר-יום-שני) כקבוצה, *12 מכונות
וירטואליות חדשות מ־vCenter*, ליד המארחים הסרוקים שהם תואמים, כך ששני הצדדים
נפגשים לפני שאחד מהם הופך למכשיר. *בדיקה ויצירה…* קוראת שוב את המקור
ויוצרת אותם באצווה אחת שאפשר לבטל; בתצוגה המקדימה אפשר לבחור שורות ולהשאיר
אחרות להמשך. *יצירה כמכשירים* שומרת על הדרך הקודמת. **החלה** ידנית על
התוכנית של המקור תמיד יוצרת כמו קודם, ועדכונים מתוזמנים לשורות שהמקור הוא
הבעלים שלהן זהים בשני המצבים. המכשיר של חומת אש או של בקר עצמו, והמארחים של
מערכת וירטואליזציה, נוצרים כמו קודם.

שורות מיובאות מופיעות תחת `source=integration` ושומרות על החותמת בכל
מיזוג מתוזמן; הוצאה משירות של מקור לא מוחקת את מה שהוא ייבא — לשם כך
מבטלים את הסנכרונים שלו.

## ביטול סנכרון

כל סנכרון זוכר כל שורה שכתב: מה יצר, וכל ערך ששינה יחד עם הערך שלפניו.
פותחים את שורת המקור (החץ ליד התג שלו) או מסיימים החלה: **סנכרונים
אחרונים** מציע **ביטול הסנכרון הזה** בכל סנכרון שכתב משהו.

הביטול מוחק את השורות שהסנכרון יצר ומחזיר את הערכים ששינה — בפעולה אחת,
מהשורה האחרונה לראשונה, בשמכם. שורה שמישהו שינה מאז הסנכרון, שורה ששורה
אחרת מצביעה עליה כעת (רשת משנה שמכילה כתובת שלכם) ושורה שנמחקה מאז
**נשמרות** ומפורטות עם הסיבה; שורה שנמחקה לעולם לא נוצרת מחדש. החלון
מסתיים בספירות — "⁨41⁩ שורות בוטלו", "שתי שורות נשמרו — שונו מאז הסנכרון" —
וברשימה.

**להשהות את התזמון של המקור** מסומן כברירת מחדל, כדי שהסנכרון הבא לא
יחזיר את השורות חמש דקות אחר כך; מפעילים את המקור מחדש כשהיקף הסנכרון
שלו נכון. אפשר לבטל סנכרון פעם אחת; הביטול נרשם כריצה משלו, עם מי ביטל
מה ומתי, וכל שורה שהוחזרה כותבת רשומה משלה ביומן השינויים. סנכרון שהוחל
לפני הגרסה הזו, ייבוא של קובץ והגירת ⁦NetBox⁩ אינם ניתנים לביטול כאן;
סנכרונים שהוחלו לעולם לא נמחקים.

## תקינות

כל סנכרון — מתוזמן או כזה שאדם החיל — נשפט לפי מה שהחזיר כל **ערוץ**.
ערוץ הוא קריאה אחת שה־connector מבצע: הממשקים, חכירות ה־DHCP וטבלת ה־ARP
של FortiGate, המחשבים ושאילתות ה־PTR של הספרייה, אובייקטי ה־host
והתעודות של Check Point. תג המצב של המקור אומר אחד מאלה:

| מצב | פירוש |
| --- | ----- |
| **תקין** | כל ערוץ שהסקופ של המקור מבקש ענה, ואף קורא לא נעצר במגבלה שלו. |
| **חלקי** | לפחות ערוץ אחד ענה, אבל ערוץ אחר נכשל, השאיר הערה או נעצר במגבלה שלו ("computers: נעצר ב־8,192 — במקור יש יותר"). מה שענה עדיין מוחל. |
| **מוחזק — ממתין לאדם** | סנכרון מתוזמן שהתשובה שלו הצטמקה (ראו למטה). דבר לא הוחל. |
| **שגיאה** | אי־אפשר היה לקרוא את המקור כלל, או שכל ערוץ שהסקופ שלו מבקש נכשל — ספק שלא החזיר דבר ממה שנתבקש הוא שגיאה, לא הצלחה שקטה. |
| **מעולם לא** | המקור עוד לא סונכרן. |

פותחים את שורת המקור (החץ שליד התג) כדי לראות **מה החזיר כל ערוץ**: המצב
שלו, השורות שהחזיר (**נראו**), השורות שנכנסו בסעיפים שהוא מזין (**הוחלו** —
לעולם לא יותר ממה שהחזיר; ערוצים שמזינים אותו סעיף חולקים את הספירה שלו)
וההערה של ה־connector עצמו. מקור חלקי מציין שם את הערוץ שנכשל, בלי לפתוח
אצווה; גם רשימת **הסנכרונים האחרונים** מראה את המצב של כל ריצה.

**סנכרון תקין אחרון** הוא עמודה משלו: הוא זז רק בסנכרון *תקין*, לעולם לא
בניסיון שנכשל, חזר חלקי או הוחזק — את הרעננות קוראים ממנו, לא מהניסיון
האחרון. מקור חלקי, מוחזק או שנכשל שולח **source.sync_failed** לערוצי
ההתראות לכל היותר פעם ביום (התקציר מציין את המצב ואת הערוץ שנכשל), ו־
**source.sync_recovered** כשהוא *תקין* שוב.

### ההשהיה

התזמון לעולם לא מחיל תשובה שנראית כמו תקלה. כשבתשובה מתוזמנת פחות שורות
מ־**השהיית תשובה שהצטמקה (%)** משורות הסנכרון התקין האחרון — 50% כברירת
מחדל — או שהיא חוזרת ריקה (אלא אם גם הסנכרון התקין האחרון היה ריק; סנכרון
ראשון שעונה ריק מוחזק), הסנכרון **מוחזק**: דבר לא נכתב, אצוות הייבוא של
הריצה נשארת טיוטה שמציינת את הסיבה, והתג אומר *מוחזק — ממתין לאדם*. ההגדרה
נמצאת בכרטיס **תזמון** (`SOURCE_SHRINK_HOLD_PCT` ב־`.env`); `0` מבטל את
ההשהיה.

כדי להחיל הצטמקות מכוונת — VDOM שהוצא משירות, ספרייה שנוקתה — פותחים את
הסנכרון של המקור ומריצים **תצוגה מקדימה**: הסקירה מציגה "בתשובה הזו 40%
מהשורות של הסנכרון התקין האחרון (תאריך)" מעל התוכנית. קוראים, ואז
**מחילים**. החלה של אדם לעולם לא מוחזקת, והחלה *תקינה* הופכת לסנכרון
התקין האחרון החדש.

### הבדיקה רצה איפה שהתזמון רץ

**בדיקה וגילוי** רצה ב־**תהליך הסריקה** — התהליך שבו התזמון רץ, עם
תרגום השמות והניתובים שלו — וה־API מריץ את אותה בדיקה לצידה, שמוצגת
כשלב **משרת האינטרנט**. שלב **תרגום השם** מראה לאיזו כתובת כל אחד מהם
תרגם את שם ה־controller; כשהן שונות, או כשאחד מגיע ל־controller והשני
לא, הבדיקה אומרת זאת, והתשובה של תהליך הסריקה היא זו שקובעת. כשאף תהליך
רקע לא רץ, הבדיקה עונה "שום תהליך רקע לא ענה — התזמון אינו פועל, ולכן
דבר לא יסונכרן" בתוך שתי דקות, במקום להיתקע.

כשהחלה מפרה כלל של מסד הנתונים (למשל שתי רשתות משנה חופפות), דבר לא נכתב
וההודעה מציינת את הכלל; הריצה שנכשלה שומרת את סוג השגיאה ואת שם הכלל,
לעולם לא את ה־SQL.

## פרסום DNS

המקורות הם חצי הקריאה; **פרסום DNS** הוא חצי הכתיבה של לולאת ה־IPAM↔DNS.
שורת *אזור* תחת הגדרות ← אינטגרציות ← **פרסום DNS** מנקנת אזור היפוך
(`in-addr.arpa` או `ip6.arpa`) ואת השרת הסמכותי שבבעלותו, ודוחפת רשומות
PTR שנוצרות מכתובות ה־IPAM שלכם. שתי תעבורות:

| סוג | שדה השרת | אישורים |
| ------------ | ------------------------- | ------------------------------------ |
| **PowerDNS** | כתובת בסיס של API ב־HTTP(S) | מפתח API בכותרת `X-API-Key` |
| **RFC 2136** | שרת שמות `host[:port]` | שם מפתח TSIG + סוד (+ אלגוריתם) |

סט הרשומות הרצוי מחושב בזמן אמת: כל כתובת IP **פעילה** עם שם מארח בצורת
FQDN שנופלת בתוך טווח ההיפוך של האזור הופכת ל־PTR מסוג `name → hostname.`
שמות מארח קצרים מדווחים כ*לא ניתנים לפרסום* בתוכנית — אף פעם לא מנחשים;
שתי כתובות הטוענות לאותו שם PTR מוזהרות כ*התנגשות* — השורה המאוחרת מנצחת.

הזרימה מראה את זו של המקורות: **בדיקה** חוקרת זמינות, אישורים וקיום האזור
במעלה הזרם; **תוכנית** מציגה את ההבדל האמיתי — שורות `add` / `update` /
`delete` / `exists` — פסק דין *התנגשות* כשרשומה זרה מחזיקה שם ש־⁦LanCompass⁩ רוצה (מדווח, לעולם לא נדרס — הסר אותה במעלה כדי לפרסם) — בתוספת מניין *זר* של רשומות PTR ש־⁦LanCompass⁩ לא יצר;
**החלה** מחשבת את התוכנית מחדש לפני הכתיבה. שליחת המספרים מתצוגת
המקדימה עם ההחלה שומרת מסחף — אזור שהשתנה מתחתיך מחזיר התנגשות, לא
פרסום עיוור.

כל שורה בתוכנית אומרת מה היא תעשה לפני שמשהו נכתב: הפעולה, שם ה־⁦PTR⁩, השם
שהוא מחזיק היום וזה שיחזיק, והסיבה במילים — *התנגשות* נקראת "רשומה זרה מחזיקה
את השם — כדי לפרסם, יש להסיר אותה בשרת ה־⁦DNS⁩" (מישהו הגדיר את ה־⁦PTR⁩ הזה
ידנית לשם אחר לפני ש־⁦LanCompass⁩ כתב אותו אי־פעם), ו*מחיקה* של שם שכבר נעלם
נקראת "כבר לא קיים בשרת ה־⁦DNS⁩ — השורה הוסרה מהרישום". ה־⁦PTR⁩ של כתובת ששוחררה — שם
ש־⁦LanCompass⁩ פרסם — הוא *מחיקה* רגילה, ו־⁦PTR⁩ ש־⁦LanCompass⁩ פרסם ומישהו
שינה אחר כך ידנית הוא *עדכון* חזרה לשם המתועד (השורה מציגה את שני השמות);
ההתנגשות מדווחת בכל פרסום ואף פעם לא נכתבת.

**הפנקס הוא הבעלים של המחיקות.** כל שם ש־⁦LanCompass⁩ מפרסם נרשם בפנקס
`dns_records`, ומחיקות מחושבות *רק* מאותו פנקס — "קיים במעלה אבל לא
בהבדל" הוא רשומה זרה: מדווחת ואף פעם לא נוגעים בה. אפשר להצביע על אזור
היפוך מאוכלס והשמות היחידים שיימחקו אי פעם הם אלה שהוא יצר. מחיקת שורת
האזור מסירה את הפנקס, לא את הרשומות — ה־PTR במעלה פשוט הופכים זרים.

הערות לאזור:

- **PowerDNS** רוכב על אותו לקוח HTTP נעוץ כמו המקורות — `verify_tls`
  נכבד, אימות בכותרת `X-API-Key`.
- **RFC 2136** קורא דרך **AXFR** נכנס (על `allow-transfer` לכלול את מארח
  ה־⁦LanCompass⁩ בצד הרחוק) וכותב `UPDATE` דינמי חתום ב־TSIG על TCP — DNS
  רגיל, בלי URL, שום דבר לא יוצא מה־LAN.
- **פרסום אוטומטי** הוא opt-in לאזור: הטיק היומי של המתזמן מריץ את אותו
  פרסום מוגבל כמו החלה ידנית ומדווח דרך אירועי `dns.published` /
  `dns.publish_failed`.
- ה־TTL חל על כל PTR שמתפרסם (רצפת 60 שניות); v1 מפרסם PTR בלבד —
  אזורים קדמיים, DNSSEC ויצירת אזור בשרת נשארים מחוץ לתחום בכוונה.

### כתיבת רשומות ⁦PTR⁩ לאזור ⁦AD⁩

אזור משולב ⁦Active Directory⁩ שמוגדר **⁦Secure only⁩** (ברירת המחדל של
אזורי ⁦AD⁩) מקבל רק עדכונים חתומים ב־⁦Kerberos⁩ (⁦GSS-TSIG⁩). עדכון לא חתום
נענה *⁦REFUSED⁩*, ועדכון חתום במפתח ⁦TSIG⁩ שבקר התחום לא מכיר — *⁦BADSIG⁩* —
ולשרת ⁦DNS⁩ של ⁦AD⁩ אי אפשר לתת מפתח ⁦TSIG⁩ משלו. ⁦LanCompass⁩ אינו חותם
ב־⁦Kerberos⁩, ולכן כשקריאת האזורים של מקור ⁦AD⁩ אומרת שהאזור מקבל עדכונים
מאובטחים בלבד, הדחייה אומרת זאת: *„האזור הזה מקבל רק עדכונים חתומים
ב־⁦Kerberos⁩ (⁦Secure only⁩) — ⁦LanCompass⁩ אינו חותם ב־⁦Kerberos⁩; ראו בפרק
⁦DNS⁩ את שתי האפשרויות”*. שתי האפשרויות:

1. **אזור מואצל.** הפעילו את האזור ההפוך ש־⁦LanCompass⁩ כותב בשרת
   ⁦PowerDNS⁩ או ⁦BIND⁩, והאצילו אותו מה־⁦DNS⁩ של ⁦AD⁩: באזור האב של ⁦AD⁩
   (`88.10.in-addr.arpa`) הוסיפו האצלה של אזור הבן (`250.88.10.in-addr.arpa`)
   לשרת הזה (רשומת ⁦NS⁩ והכתובת שלה). ⁦LanCompass⁩ כותב אז לשם עם מפתח
   ⁦API⁩ או מפתח ⁦TSIG⁩, ולקוחות ⁦Windows⁩ עדיין מתרגמים את השמות דרך
   ה־⁦DNS⁩ של ⁦AD⁩.
2. **⁦Nonsecure and secure⁩, באזור ההפוך בלבד.** ב־⁦DNS Manager⁩, *מאפיינים ←
   עדכונים דינמיים ← ⁦Nonsecure and secure⁩* של האזור ההפוך. כל מחשב שמגיע
   לבקר התחום יכול אז לשנות את הרשומות של האזור הזה — הגבילו את זה לאזור
   ההפוך ש־⁦LanCompass⁩ מפרסם, ולעולם לא לאזור ישיר.

חתימה ב־⁦Kerberos⁩ (⁦GSS-TSIG⁩) היא החלטה בפני עצמה (⁦D-KRB⁩, שהתשובה עליה
לעת עתה היא *לא*) והייתה מוסיפה תלות בזמן ריצה.

## כלי ניטור

‏⁦LanCompass⁩ הוא התיעוד של מה שהרשת היא ושל מה שנצפה בה לאחרונה — לא
מאגר מדדים. העבודה מתחלקת כך:

- **‏⁦LanCompass⁩ שומר** את המלאי, את המצב הנוכחי של כל יעד ניטור, את
  המעברים ואת הזמינות היומית שלו, את התקלות ואת מי שקיבל אותן לטיפול
  ([ניטור](/he/docs/monitoring/)).
- **כלי הניטור שלכם שומר** את הסדרות, את לוחות המחוונים ואת הזימון —
  ⁦Prometheus⁩ ו־⁦Grafana⁩, ‏⁦Zabbix⁩, ‏⁦LibreNMS⁩, ‏⁦Checkmk⁩, ‏⁦Icinga⁩.

שלושה חיבורים מקשרים ביניהם, וכולם לקריאה בלבד בצד של ⁦LanCompass⁩:

1. **הדגימה** — ⁦`GET /metrics`⁩ בפורמט הטקסט של ⁦Prometheus⁩: מסלול
   הניטור (יעדים לפי מצב, יעדים שהבדיקה שלהם מאחרת, הסבב האחרון, המחזור
   של המתזמן), מסירות לפי סוג ערוץ ותוצאה, תקלות פתוחות ותקלות שאיש לא
   קיבל לטיפול, מסלול ⁦SNMP⁩; סדרות לכל יעד רק לדוגם שמחזיק
   ב־⁦`METRICS_TOKEN`⁩ ([ניטור ← כלי ניטור](/he/docs/monitoring/#monitoring-tools)).
2. **הקליטה** — כללים של ⁦Prometheus⁩, ‏⁦Grafana⁩ ו־⁦Alertmanager⁩ שולחים
   אל ⁦`POST /api/v1/events/alertmanager`⁩ כמקבל ⁦webhook⁩; כל כלי אחר
   שולח אל ⁦`POST /api/v1/events`⁩ עם ⁦`dedup_key`⁩ ([אסימוני ⁦API⁩ ←
   אירועים נכנסים](/docs/api-tokens)). בשני המקרים ההתראה מגיעה לערוצים
   וליומן השינויים של ⁦LanCompass⁩ פעם אחת לכל מצב.
3. **הקישור** — לחצן **גרפים** בכל דף מכשיר, שנבנה מהתבנית
   ב־**Settings → Monitoring** (⁦`external_graph_url_template`⁩), פותח את
   הגרפים של המכשיר בכלי שלכם.

ה־⁦API⁩ עונה בכתובת ⁦`API_BIND:API_PORT`⁩. קובץ ⁦`.env`⁩ שנוצר מ־⁦`.env.example`⁩
מאז ⁦V134⁩ מגדיר ⁦`API_BIND=127.0.0.1`⁩ — כתובת הלולאה המקומית בלבד — וקובץ
ישן יותר (או היעדר הגדרה) משאיר ⁦`0.0.0.0:8001`⁩, כל הכתובות של המארח. כשה־⁦API⁩
על הלולאה המקומית, דוגם או מנהל התראות במארח אחר צריכים ⁦`API_BIND`⁩ שמוגדר
לכתובת שהם מגיעים אליה (⁦`0.0.0.0`⁩), או ⁦reverse proxy⁩ שמעביר את
⁦`/metrics`⁩ ואת ⁦`/api/v1/events`⁩.

הדוגמאות שלהלן דורשות אסימון ⁦API⁩ עם ⁦`data:write`⁩ (**Settings → API
tokens**); ⁦`https://ipam.example.com`⁩ מייצג את ההתקנה שלכם.

### ⁦Alertmanager⁩, ⁦Grafana⁩

מקבל ⁦webhook⁩ (ב־⁦Grafana⁩: נקודת קשר מסוג ⁦Webhook⁩) שמכוון לנקודת
הקליטה, עם האסימון כאישור ה־⁦bearer⁩ שלו:

```yaml
receivers:
  - name: lancompass
    webhook_configs:
      - url: https://ipam.example.com/api/v1/events/alertmanager
        http_config:
          authorization:
            credentials: ipam_a1b2…
        max_alerts: 100
```

כל התראה הופכת ל־⁦`external.alertmanager.<alertname>`⁩ (באותיות קטנות),
עם המפתח ⁦`{fingerprint}:{status}:{startsAt}`⁩: החזרות של קבוצה
ב־⁦Alertmanager⁩, והניסיונות החוזרים שלו, מגיעים פעם אחת.

### ⁦Zabbix⁩

סוג מדיה ⁦Webhook⁩ (**Alerts → Media types**) עם הפרמטרים ⁦`url`⁩ =
⁦`https://ipam.example.com/api/v1/events`⁩, ‏⁦`token`⁩, ‏⁦`subject`⁩ =
⁦`{ALERT.SUBJECT}`⁩, ‏⁦`host`⁩ = ⁦`{HOST.NAME}`⁩, ‏⁦`severity`⁩ =
⁦`{EVENT.SEVERITY}`⁩, ‏⁦`event_id`⁩ = ⁦`{EVENT.ID}`⁩, ‏⁦`status`⁩ =
⁦`{EVENT.STATUS}`⁩, והסקריפט הזה:

```javascript
var p = JSON.parse(value);
var req = new HttpRequest();
req.addHeader('Content-Type: application/json');
req.addHeader('Authorization: Bearer ' + p.token);
req.post(p.url, JSON.stringify({
  event_type: 'external.zabbix.' + (p.status === 'RESOLVED' ? 'resolved' : 'problem'),
  summary: p.subject,
  source_name: 'zabbix',
  dedup_key: p.event_id + ':' + p.status,
  payload: { host: p.host, severity: p.severity }
}));
if (req.getStatus() >= 300) throw 'LanCompass answered ' + req.getStatus();
return 'OK';
```

## מדריכי connectors

מדריכי הכנה לכל פלטפורמה — אישורים, תפקידי הרשאות מינימליות, מה כל
connector קורא, והסתייגויותיו הכנות:

- **[Check Point](/he/docs/checkpoint/)** — ה־Web API של שרת הניהול, פרופיל
  admin לקריאה בלבד, והקריאה הדו-שלבית ל־gateways.
- **[vCenter / ESXi](/he/docs/vcenter/)** — אימות session של vSphere REST,
  תפקיד Read-only, ושער ה־VMware-Tools על IPs של guests.
- **[Proxmox](/he/docs/proxmox/)** — אימות API token, תפקיד PVEAuditor,
  והסתייגות ה־QEMU guest-agent.
- **[FortiGate](/he/docs/fortigate/)** — אסימון של REST API admin, סקופ לפי
  VDOM, קריאות נקודות ה־monitor.
- **[PAN-OS](/he/docs/panos/)** — ה־keygen החד-פעמי, אימות כותרת `X-PAN-KEY`,
  סקופ vsys/Panorama, קריאות `show`-בלבד.
- **[Nutanix Prism](/he/docs/nutanix/)** — אימות Basic של Prism Central,
  GETים של v4 וגיבוי list-RPC של v3, קישור אורח→host.
- **[UniFi](/he/docs/unifi/)** — מפתח `X-API-KEY` מהקונסולה, ה־Integration
  API, אתרים כסקופ.
- **[Omada](/he/docs/omada/)** — client-credentials של OpenAPI, לחיצת יד
  האסימון, סקופ לפי אתר, והסתייגות ה־v2 של 6.2.
- **[MikroTik](/he/docs/mikrotik/)** — REST של RouterOS על www-ssl, אימות
  Basic, ולמה GET-only הוא תשתיתי שם.
- **[Active Directory](/he/docs/activedirectory/)** — LDAP קריאה־בלבד מול
  Domain Controller: אובייקטי מחשב, טופולוגיית Sites & Services
  והעשרת שמות מחשב ב־PTR.
- **[NetBox](/he/docs/netbox/)** — שיקוף GET-only מאומת־אסימון של NetBox חי:
  אתרים, מכשירים, prefixes, כתובות IP — ובמה הוא שונה מייבוא הקובץ
  החד־פעמי.

⁦UniFi⁩, ⁦Omada⁩, ⁦MikroTik⁩ ו־⁦OPNsense⁩ הם **שכבת קהילה — ממשיכים לעבוד, בלי קריאות חדשות**: כל אחד ממשיך לסנכרן את מה שקרא קודם, ו־*בדיקת חיבור* מציגה את הקריאות האלה; לא נוסף להם שום דבר חדש.

מסגרת ה־connectors בולעת kinds חדשים בלי שינוי מודל נתונים — טופס
ה־credentials מסתגל למה שה־kind מצהיר (שדה אסימון אחד או צמד), וכל מדריך
מכסה את ההכנה בצד ה־controller מקצה לקצה.
